## 逐条答复

**Q-01 身份**
- 结论：从医生表鉴权，只能查询当前医生名下患者的数据。
- 现状：raapi 目前没有登录鉴权，接口直接信任请求参数 `doctorId`；患者范围按 `patient_relation_doctor.doctor_id` 过滤。前端登录为演示账号。
- 是否接受推荐：接受「请求中的 doctorId 只做一致性校验、不赋权」的方向；具体鉴权方式（会话 / Token）由后端结合医生表实现。

**Q-02 数据范围**
- 结论：本期只有一种角色「医生」，只看本人名下患者。二期增加「管理员」，可查全部医生的全量数据。
- 现状：没有中心字段、没有角色表。
- 本期不做中心权限、不做管理员。

**Q-03 研究库映射**
- 结论：`patient_relation_doctor.research_type` 就是研究库：

  | research_type | 研究库 | 是否 RA |
  |---|---|---|
  | 0 | 类风湿关节炎研究平台 | 是 |
  | 1 | 益赛普研究系统 | 是 |
  | 2 | 瘀血痹胶囊真实世界研究 | 是 |
  | 3 | 尪痹胶囊 | 是 |
  | 4 | 痹祺胶囊 | 是 |
  | 6 | 强直性数据库（AS） | 否 |
  | 7 | 疗效可视化研究 | 是 |

- 现状：RA 白名单 `0,1,2,3,4,7` 只在 `ProjectMapper.xml` 的 `raResearchTypes` 一处配置，5、9、999 不算 RA。统计按 `patient_basic_info.id` 去重；同一人多个 id 不合并；脱落为 `miss=1`；删除随访为物理删除。

**Q-04 导出身份字段**
- 结论：导出的数据格式待业务方确认。
- 现状：现有随访导出（`/api/ra/export/visitsCsv`）含患者ID（内部 `patient_basic_info.id`）、研究编号、姓名（脱敏），不含手机号、身份证号。

**Q-05 / Q-06 / Q-07 基线、当前评估、6m 取哪次访视**
- 结论：待医学负责人确认。开发可先按清单推荐方案做，并标为假设。

**Q-08 阈值与精度**
- 结论：用 DAS28-CRP 专用阈值（2.3 / 2.7 / 4.1）。
- 现状：患者列表 / 详情现用 2.6 / 3.2 / 5.1，判定值为老系统存的 `bqpg.result.crpScore`（2 位小数）。若统一改为 CRP 专用阈值，列表的疾病活动度也要同步改（raapi `Das28Util`）。
- 精度：未单独答复，建议沿用 2 位小数 canonical 值判定、页面再按需显示。

**Q-09 组成项、单位、关节 / HAQ 缺失规则**
- 结论：需与老系统确认，找胜凯。
- 现状（供参考）：GH = `ztScoreByPatient`、疼痛 = `tjScore`、医生评分 = `ztScoreByDoctor`，均 0~100 整数；单位 CRP mg/L、RF IU/mL、抗CCP U/mL（字段字典已确认）；HAQ 按老系统算法（8 维度各取最大值后平均，已与老系统逐位一致）；手部关节编号 1~20 的对照未确认。

**Q-10 只有 DAS 结果、缺组成项的历史数据**
- 结论：可以使用老数据里的结果（如 `result.crpScore`）。

**Q-11 药品字典**
- 结论：有药品字典表，表名找胜凯。
- 现状：随访的西药 / 中成药清单（`zlfa.xyList` / `zcyList`）是自由录入的 `drugName`、`goodsName`、`category`、`company` 等，尚未与字典表关联。

**Q-12 用药历史不完整**
- 结论：空的用药模块 = 没填，不当作停药。
- 其余（起止日期格式与可信度、估算起始日、再次启用同药）：未答复，按清单推荐方案做并标为假设。

**Q-13 血清学**
- 结论：待医生 / 业务方确认（曾经阳性还是最近一次、ULN、时间截断）。
- 现状：患者列表的疾病分型现按「最近一次有结果的随访」，RF ULN 20 IU/mL、抗CCP ULN 25 U/mL（配置 `ra.serology.*-uln`），都没查为「未检测」；分型不落库。

**Q-14 年龄、时长与时区**
- 结论：临床业务时区定为 **Asia/Shanghai**；年龄用身份证号推算出生日期后计算。
- 现状：raapi 已有 `IdCardUtil` 按身份证号算周岁；无有效身份证号时用「建档年份 − 建档时年龄」估算（不精确，建议带质量标识）。

**Q-15 资料完整的缺失规则**
- 结论：待定。
- 现状：现有 4 条缺失规则（缺 DAS28、缺基线检验、缺合并疾病、缺用药史，见 `ProjectMapper.xml`），没有问题关闭 / 忽略状态。

**Q-16 统计实现**
- 结论：用 Java，在现有 Spring Boot（raapi，JDK 8）内实现，不另起 Python 服务。

**Q-17 统计参数与未知分母**
- 结论：待定。需要先向需求方说明这些参数（显著性水平、卡方 / Fisher 切换、Mann-Whitney 方法、分位数算法、未知值是否进分母）后再定。

**Q-18 自动发现的临床表述**
- 结论：不需要（不做自动发现文案）。

**Q-19 保存队列共享**
- 结论：不需要。

**Q-20 保存成员快照**
- 结论：不需要。

**Q-21 接口、入口与分页**
- 结论：按 raapi 工程现有规范：路径 `/api/ra/<业务>/<接口名>`，统一返回 `DataResult`，Controller / Service / Mapper / VO 分层，每加 / 改一个接口同步更新 `docs/API.md`。不加 `/api/v1` 网关别名。

**Q-22 旧系统写入路径与数据新鲜度**
- 结论：与老系统共用同一个数据库（wenwen），老系统仍在写入同一批表。
- 现状：随访表无可靠的 `updated_at`。
- 建议：直接实时查库，不做缓存 / 离线计算，避免与老系统写入不一致；如确需缓存，再与技术负责人确认刷新策略。

**Q-23 数据库、后台执行与保留策略**
- 结论：待定，找胜凯（生产 MySQL 版本、部署、文件存放、保留期）。
- 已知：开发库为 MySQL 8（支持 `JSON_TABLE`、`ROW_NUMBER`）；新功能数据放新表，建表 SQL 放 `src/main/resources/sql/`。

**Q-24 DeepSeek 外发**
- 结论：账号找贵玉；外发内容、保留政策待定。

**Q-25 无法表示的自然语言**
- 结论：识别不了或部分识别时，由 AI 生成给用户的提示语（说明哪些条件没识别、给出可用的问法示例），不静默扩大筛选范围。

**Q-26 历史导出权限**
- 结论：沿用现有规则：从当前月份往前 6 个自然月内可直接下载（如 10 月可下 4 月 1 日至今），更早的提交申请。配置 `ra.export.free-months=6`。

**Q-27 审批链路**
- 结论：不需要审批流程。提交申请后发邮件通知管理员即可。
- 现状：申请已记录到 `export_application`（`mail_sent` 标记是否已发）；发邮件功能待实现，管理员邮箱配置 `ra.export.apply-mail-to` 待提供。

**Q-28 PT03 与 SPSS / Stata 导出**
- 结论：待定，需求方说明 PT03 指什么接口、是否必须导出 SPSS / Stata 原生格式。
- 现状：raapi 里没有名为 PT03 的接口；前端原型的「数据导出」注释里出现过「后端导出接口 PT03」，目前实际的导出接口是 `/api/ra/export/visitsCsv`（CSV）。

**Q-29 性能验收**
- 结论：不做性能验收。

**Q-30 医学 / 统计基准与上线数据质量门槛**
